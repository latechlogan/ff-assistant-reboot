# ff-assistant-reboot — Trust layer

<!-- Written by project-kickoff, Phase 5. Read when writing tests, adding a check, or deciding whether green means done. /vet reads this and dispatches the reviewer. -->

## What green means here

Passing checks mean the code does what the acceptance criteria say and nothing
mechanical is broken. **They do not mean the right thing was built.** Logan reviews at
milestones — against the sequence diagrams in `docs/architecture.md`, the criteria on
each ticket, and the slice boundaries — not line by line.

The 2026 tool had 653 passing tests and Logan did not trust them, because the agent
that wrote the code wrote the tests, in the same context, and nobody critiqued either.
Everything below exists to break that loop.

## Acceptance criteria

Every **ticket** (`tickets/NNN-slug.md`) carries a `## Done looks like` section of
numbered, checkable statements, **approved by Logan before implementation starts**.

Tests are named after the criterion they prove **and the ticket it belongs to** —
three digits, a space, the AC id, an em dash:

```ts
test("001 AC7 — value column sums to the distributable pool over available rows only", …)
//    ^^^ the ticket
```

The ticket number is not decoration. Without it, ticket 009's AC4 was satisfied by
ticket 001's test about bye weeks, and any ticket's AC1 satisfied every ticket's AC1
(ticket 011). Grep for one ticket's coverage with `grep -rn '"005 AC' src test`.

A test that traces to no criterion is either a regression guard for a logged learning
(say so in the test name: `REG 2026-09-15 — bye rows carry no gp field`) or a candidate
for deletion.

`pnpm criteria` matches each ticket's AC ids against the tests named for **that**
ticket, and exits non-zero if a criterion has no test, if a test names a ticket or an
AC that does not exist, or if an `in-progress` ticket has no criteria at all. It is a
gate: it fails loudly or it is worthless.

- `pnpm criteria` checks every ticket that is not `done` or `dropped`, and prints what
  it skipped, by name and status. A gate that silently checks nothing is worse than one
  that fails — ticket 008 went unchecked for exactly that reason.
- `pnpm criteria tickets/NNN-*.md` checks those tickets whatever their status. This is
  the scoped form `/vet` uses for the ticket in flight.

It runs in `/vet`, not in `pnpm check`, because the default form reports on work that
has not been started yet — an untested criterion on an `open` ticket is news, not a
broken build. Its own behaviour is tested in `test/criteria.test.ts`, against fixture
tickets in a temp directory rather than against this repo's state.

A criterion no test can reach — a lint rule, a check against the private data repo —
says so in the ticket in parentheses: `(proved by \`pnpm check\`)`, `(proved by hand
2026-09-22: …)`. It passes, and the run prints the annotation every time, so a reviewer
can argue with the claim.

## Who writes the tests

| Work | Tests written by | Why |
|---|---|---|
| **Core pricing math** (`src/core/scoring`, `survival`, `valuation`, `bids/price`) | A **separate agent**, from Logan's approved criteria, **before** the implementation exists | The strongest independence available: the implementer has to satisfy tests it did not author and cannot quietly reshape |
| Everything else (adapters, CLI, wiring) | The implementer | Cheaper, and the reviewer plus mutation testing covers the gap |

## Test layers

| Layer | Exists | Protects against | Runs in |
|---|---|---|---|
| Unit (pure core) | Yes | Wrong math: local scoring, survival weights, replacement level, VORP, the FAAB allocation, curve percentiles | check command |
| Integration (fixtures → board) | Yes | Wiring and shape errors — the whole 2026 category: byes arriving with no `gp` field, chopped rosters as `players: null`, rosters holding more players than the roster shape allows | check command |
| Golden + determinism | Yes | Silent numeric drift, and two runs of the same inputs differing | check command |
| Live smoke | Yes, by hand | The feed changing shape underneath us | `pnpm smoke --live`, run before a real Tuesday. **Never** in the check command — it needs a network |

Tests run against scrubbed real payloads in `test/fixtures/`, regenerated by
`pnpm fixtures`; see `docs/data-model.md`.

## The check command

`pnpm check` runs, in order:

1. `prettier --check .`
2. `eslint .`
3. `tsc --noEmit` (with `erasableSyntaxOnly`)
4. `depcruise src` — including the **core purity rule**: nothing in `src/core/**` may
   import `node:fs`, `node:http`, `fetch`, or anything from `src/adapters/**`
5. `vitest run`
6. `pnpm privacy-scan` — fails on a real Sleeper handle, owner ID, or league ID in any
   tracked file
7. `gitleaks git --no-banner`

**Everything that gates work calls this and nothing else** — the Stop hook, pre-push,
CI. If a check is not in here, it is not enforced. One command also means CI can never
enforce less than the local machine does.

If the suite ever grows past ~10 seconds, split it: the Stop hook runs format, lint and
typecheck; `/vet` and pre-push run the whole thing. Not needed at v1 size.

## Mechanical vs judgment

**Mechanical (hooks, written at scaffold time, Logan approves):**

- PostToolUse on Edit|Write: `prettier --write` on the touched file
- Stop: `pnpm check || exit 2`

**Judgment (REVIEW.md) — no test can catch these:**

- Is a new curve **measured or invented**? A reasonable-looking shape with no data
  behind it is the failure this project exists to prevent.
- Does a closed-economy assertion say **which population** it closes over? Summing
  `value` across every row of a 2026 board gives ~$6,526 against a $3,600 pool, because
  ~2,900 players sit at the $1 floor. A test can pass and mean nothing.
- Does any output **overclaim**? The bid range describes what winners paid, which ran
  ~1.4× what was needed to win. Copy that blurs "worth" and "what it costs" is a
  should-fix, and so is any claim of edge (one season is n=1).
- Did any number pass through an LLM?
- Is there a literal team count, budget, FAAB amount, or roster shape in the code?
- Is a new display column **on trial with a stated expiry**, per the brief's rule?
- Do fixtures contain a real handle, owner ID, or league ID?
- Does `--debug` still trace the sequence in `docs/architecture.md`? A trace that has
  drifted from the diagram is a finding about one of them.
- Was this delivered in slices small enough to review one at a time?

## Mutation testing

**Enabled, scoped to the pure core:** `src/core/scoring`, `src/core/survival`,
`src/core/valuation`, `src/core/bids`. Tool: Stryker. Threshold: **70% to start**,
raised once we see where it lands — a threshold set too high on day one only teaches
everyone to ignore it. Run with `pnpm mutate`, from `/vet`, never from the Stop hook.

Why here and not everywhere: this is where wrong-and-green is expensive. A bad
allocation produces a plausible number, and a plausible number becomes a real bid.
Mutation testing on a fetch wrapper is noise.

## The reviewer

`.claude/agents/reviewer.md` is an independent agent with its own context window. It
receives the ticket and the diff, reads this file and REVIEW.md, runs the check
command, and reports must fix / should fix / fine as is. **It never reads the
conversation that produced the code** — that separation is the whole point, and it is
why the reviewer is a subagent rather than a prompt in the same session.

## For /vet

When the scaffold writes this project's `/vet`, its body should:

1. Run `pnpm criteria tickets/NNN-*.md` for the ticket in flight first — an acceptance
   criterion with no test named for **that** ticket is a stop. Run the bare
   `pnpm criteria` too, for the rest of the board; untested criteria on tickets nobody
   has started are context, not a stop.
2. Run `pnpm mutate` when the diff touches `src/core/**`; report surviving mutants.
3. Dispatch the `reviewer` subagent with: the current ticket file, `git diff main`, and
   the paths to `docs/trust.md` and `REVIEW.md`.
4. Return the reviewer's report unchanged. Do not soften it, summarize it, or argue
   with it in the same message.
